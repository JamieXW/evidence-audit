Collision certificates: checkable evidence that a target is out of reach

Jamie Wang

Independent project · November 2026

Abstract. A benchmark target that depends on information the solver never sees makes every reward too small. Abundant's validation notebooks catch this with analysis that reviewers then audit. This note asks which audit claims a program can check instead. It builds the checker for one type, collisions: cases the solver cannot tell apart that have different answers. The ceiling for every solver turns out to need no auditor, because the checker can compute it. What an auditor adds is a choice of columns to ignore, and that choice can be tested. On a synthetic benchmark, a held-out test flags 27 of 28 misleading column choices with no false flags, and recovers all 20 tasks where exact matching proves nothing. The same machinery gives a pairwise F1 ceiling, a two-sided interval around a target, and a tripwire for scores that should be impossible.

Status: pilot on 120 synthetic tasks. No language model was tested.

1Motivation and question

This project grew out of my work on a business knowledge assistant at Leader Lane, which answers questions from company documents. Some questions cannot be settled by the documents the assistant is given, and a wrong answer alone does not say whether the assistant failed or the question was unanswerable. Abundant's post describes the same problem for research agents. This project is independent of that work and uses no company data.

Abundant's post on setting realistic targets[1] measures an agent's progress as

reward = (score − start) / (target − start)

where start is a naive baseline and target is the best score a strong solver could realistically reach. If the target is too high, every reward shrinks by the same factor. The post audits each target with a validation notebook, written by an agent, checked by a second agent, and reviewed by a domain expert.

Each of the post's three case studies turns on a different kind of claim. Each kind names something a program could recompute, so the reviewer checks a short list of facts and not the whole analysis.

The collision argument itself is the post's: its second case study groups cases with identical inputs and takes the majority answer. This note builds the checking around it and measures where it holds.

2A collision is a proof

Take a table of 72 loan applications. The solver sees three columns and must predict approved. A fourth column, an underwriter override, is withheld. The proposed target is 68 correct, which is what an oracle given every column scores.

Whatever the solver answers for this pattern, at least two rows are wrong. The same count works for any group: its size minus its most common label. Seven groups in this table force 9 errors, so no solver limited to the visible columns scores above 63, and the target of 68 is refuted. With a start of 37, rewards measured against 68 are at most 0.84 of rewards measured against 63.

The bound covers deterministic solvers. One that randomizes among identical rows obeys it on average and can beat it by luck, which section 7 quantifies.

3What an auditor's certificate adds

A certificate is a list of row groups. The checker accepts a group only if its rows exist, match on the declared columns, and carry different labels, and then counts the forced errors itself. A wrong or partial certificate can only loosen the bound.

When the groups match on every visible column, the certificate adds nothing. The checker holds the same table and can compute the exact ceiling without help. An auditor contributes only by declaring a subset of columns to match on, which yields a narrower claim: no rule using just those columns reaches the target.

That narrower claim is the one that matters on realistic data. The benchmark's stress tasks add one near-unique visible column, like a dollar amount. No two rows match on everything, so the ceiling for every solver is a perfect score and nothing is refuted: 0 of 20. The post meets the same wall. Counting only identical inputs puts its antibody ceiling near 0.999, and its adopted target comes from restricting to four features.

A restricted claim is true as worded and can still mislead. If a dropped column carries signal, a solver that uses it can beat the bound. So the question for a restricted certificate is whether the dropped columns matter, and section 5 tests that.

4Benchmark

There are 120 synthetic tasks: five families (loans, inventory, invoices, budgets, attendance), four scenarios each, six variants per scenario. Each task has 72 evaluation rows and 144 labelled practice rows from the same generator, standing in for the training data a solver would get. Two families are held out.

On the core set the exact ceiling refutes all 40 unsupported targets and no supported one. The second and third variants are there so that "something is hidden" cannot stand in for "the target is wrong".

5Testing the choice of columns

Given a restricted certificate, the check fits two simple lookup learners on the practice rows, one using the kept columns and one using all visible columns, and scores both on the evaluation rows. A permutation test, shuffling the dropped columns among practice rows that share kept values, says whether the gain is more than chance.

If no signal is detected, the certificate is promoted: its bound becomes the restricted ceiling plus a 95% upper bound on what the dropped columns could add. A promoted result is statistical. It is reported separately and never counted as a proof.

The one unflagged case is borderline (p = 0.065, a gain of 3 rows). Its promoted bound includes the uncertainty on that gain and stays above the target, so no supported target is refuted. When the dropped column is pure noise, the test flags 1 of 100 tasks.

The stress set goes from 0 of 20 refuted to 20 of 20, as a statistical claim with its assumptions stated. The confidence is specific to this learner and this much practice data. A stronger learner might find signal that this one misses.

6A two-sided interval

A ceiling alone can only say a target is too high. With practice rows, each task also gets a floor: the evaluation score of a solver trained only on practice data, with its columns chosen by cross-validation. Some solver reaches the floor, so the best achievable score lies between floor and ceiling.

A target above the ceiling is refuted. A target at or below the floor is witnessed, because a solver reached it. Anything between is open.

The stress tasks stay open under the proof and are settled only by the promoted bound from section 5. The measured floor also differs from what the generator's rule predicts for a single 72-row draw, by 7 rows below to 10 above on the withheld variant. A realistic score has to be measured.

7Pairwise F1 and a tripwire

Pairwise F1. The post's antibody case scores clusterings by F1 over pairs, where accuracy's count does not apply. Each group of indistinguishable pairs gets one call, same or different. Sorting groups by their share of truly-same pairs and taking the best prefix gives the highest F1 any such rule can reach; tests confirm this against brute force.

The bound covers rules that decide each pair from that pair's own features. A toy clonal task (48 cells, 12 clones, sibling clones that differ only in a hidden light chain) shows the limit.

With two pair features the baseline beats the ceiling, because linking through other cells uses information those features lack. Adding a chain feature brings it inside. The post's four features include a chain distance, and this shows why it is needed.

Tripwire. A submitted result above the ceiling for every solver means the solver saw something it should not have, or the score is wrong. The tripwire rescores the predictions, bounds the chance of beating the ceiling by randomizing among identical rows, and raises an alarm below 1%.

The last row is the limit. A withheld-column leak gains only a few rows, and on 72 rows the alarm needs about 6 to 10 rows of excess. It catches gross leaks and misses subtle ones at this size.

8A question about the post's antibody target

The post's adopted antibody target, 0.8922, is computed the way section 2 computes a ceiling: group pairs by identical values of four features and take the majority using the hidden answers. Two things follow from the results above.

  • It is an in-sample figure. Section 6 shows this kind of bound sitting above what a practice-trained solver reaches. With pairs drawn from about 50,000 cells per person the groups are probably large and the slack small, but the post does not report it. Learning the majorities on some people and scoring on others would measure it.
  • It bounds rules on four features, not every solver. The post puts the limit for any heavy-chain method near 0.999. A solver that uses more of the heavy chain could score above 0.8922, which would put its reward above 1. Whether the remaining features carry signal is what the test in section 5 is for.

This is a question from outside. The post's authors have the data and may already have checked both points.

9Related work

  • Proving a task is broken. SpecGuard[2] formalizes a coding task's description and its tests in Lean and has the proof checker decide whether any implementation can satisfy both. It is the closest precedent: machine-checked evidence that a task cannot be done as specified. It covers text against tests; this note covers inputs against labels.
  • Impossible tasks as detectors. ImpossibleBench[3] builds tasks that are impossible by construction, so any pass reveals a shortcut. The tripwire applies the same logic to scores above a proven ceiling.
  • Label errors. Northcutt et al.[4] found label errors across ten widely used test sets with confident learning,[5] and Vendrow et al.[6] re-annotate benchmarks to remove them. That work repairs individual labels. A collision ceiling takes the labels as given and measures what the inputs cannot distinguish.
  • Bayes error. FeeBee[7] evaluates estimators of the Bayes error, the lowest error any classifier can reach on a distribution. The collision ceiling is a narrower object: an exact bound for one finite table, not an estimate for a distribution.

10Limitations

  • One claim type of three. Leakage and physical-floor claims are sketched in Table 1 and not built. They decide two of the post's three case studies.
  • Small and synthetic. Twenty scenarios, five rules, one author. Each table has only 18 distinct visible patterns in 72 rows, which is why exact matching works on the core set at all.
  • Truth comes from the generator. Supported and unsupported are defined by the generating rule. The floor in section 6 is measured separately and agrees, but only on data this generator made.
  • The promotion test is learner-specific. It speaks for a lookup learner on 144 practice rows, with a normal approximation for its upper bound.
  • The F1 bound covers per-pair rules only, and the tripwire misses small leaks on small tables.
  • No model was tested. Comparing a model's bare verdict with a verdict plus certificate would show little: certified false alarms are zero by construction, and a model with tools would write the group-by. A useful experiment would give an agent a prose description of what the solver sees and data where the matching columns have to be discovered. That is not built.
  • An earlier version failed. It used short text tasks, and a regular expression solved all 80 before any model was run. It stays in the repository with that result pinned as a test.

11Reproducing the results

Tested on Python 3.12 and 3.14, standard library only. Code, data and tests are in the repository.[8]

python3 -m unittest discover -s tests
python3 ceiling.py build
python3 ceiling.py demo
python3 ceiling.py control --split all
python3 ceiling.py interval --split all
python3 ceiling.py tripwire --split all

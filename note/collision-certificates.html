Collision certificates: checkable evidence that a target is out of reach

Jamie Wang

Independent project · November 2026

Abstract. A benchmark task usually comes with a target: the score a strong solver should be able to reach. If the target depends on information the solver never sees, every reward measured against it is too small. This note describes a small tool that can prove a target is too high. The proof is a list of rows the solver cannot tell apart that have different correct answers. A program checks the list against the data, so a wrong claim cannot pass. On 100 synthetic tasks, a short script finds every provable case and raises no false alarm. On 20 harder tasks built to look more like real data, nothing can be proved about every solver. A narrower proof, limited to rules that use a chosen set of columns, covers all 20, but a reviewer has to accept the choice of columns.

Status: pilot on synthetic data. No language model was tested.

1Motivation and question

This project grew out of my work on a business knowledge assistant at Leader Lane, which answers questions from company documents. Some questions cannot be settled by the documents the assistant is given, and a wrong answer alone does not say whether the assistant failed or the question was unanswerable. Abundant's post describes the same problem for research agents. This project is independent of that work and uses no company data.

Abundant's post on setting realistic targets[1] measures an agent's progress as

reward = (score − start) / (target − start)

where start is a naive baseline and target is the best score a strong solver could realistically reach. If the target is too high, every reward shrinks by the same factor.

In the post's second case study the solver sees only part of each antibody. The validation notebook groups cases that look identical to the solver, takes the majority answer in each group, and counts the errors that no rule could avoid. That counting argument belongs to the post. It is the starting point here, and nothing in this note improves on it.

The post also describes three layers of review, each checking the one before. This note looks at one link in that chain. When an auditor, human or model, claims a target is out of reach, can the claim be packaged so that a program checks it and nobody has to trust the auditor?

Three things are added:

  • a certificate format and a checker that stays correct when the certificate is wrong or incomplete;
  • a synthetic benchmark that includes cases where something is hidden but the target is still fine;
  • measurements of where the argument stops working.

2A collision is a proof

Take a table of 72 loan applications. The solver sees three columns and must predict approved. A fourth column, an underwriter override, is withheld. The proposed target is 68 correct, which is what an oracle given every column scores.

To the solver these five rows are the same row. Whatever it answers, at least two are wrong. The same count works for any group: its size minus its most common label.

Seven groups in this table have mixed labels, and together they force 9 errors. No solver limited to the visible columns can score above 63. The target of 68 is refuted. With a start of 37, rewards measured against 68 are at most 0.84 of rewards measured against 63.

3The checker

A certificate is a list of row groups. The checker keeps a group only if its rows exist, are distinct, match on every visible column, carry at least two different labels, and reuse no row from another group. It then counts the forced errors itself.

  • A bad certificate cannot produce a false refutation. Rejecting or dropping groups only loosens the bound. Tests fuzz this with random groups.
  • Nothing is specified by hand. The check runs against the table, so there is no separate formal model that could disagree with the data.
  • It works in one direction. It can show a target is too high. It cannot show a target is right.

The bound covers deterministic predictors that use only the visible columns. A randomized predictor obeys it on average.

4Benchmark

There are 120 synthetic tasks: five families (loans, inventory, invoices, budgets, attendance), four scenarios each, six variants per scenario. Each family has its own labelling rule. Two families are held out.

The second and third variants are the hard negatives. Something is hidden, but it does not matter, so an auditor that flags every withheld column is wrong.

Ground truth comes from a reference solver: the best visible-only predictor under the generating rule. A target is unsupported when that solver falls short of it.

5Results without a model

Six reference auditors, none of them a language model, were scored on the 100 core tasks.

The row in bold is the reason for the design. That auditor groups rows carelessly and announces refutations with confidence. It is wrong about 47% of the supported tasks. The checker rejects 98% of its groups and certifies none of its claims.

The certificate proves less than the truth. It shows 63 is the limit, while the reference solver reaches 55. The difference is rows a solver could only get right by memorizing them.

6Narrower certificates for realistic features

In the stress variant one visible column is nearly unique, like a dollar amount. No two rows match on everything, so nothing can be certified for every solver: 0 of 20, although the targets are just as unreachable.

The post meets the same wall. Counting only identical inputs puts its antibody ceiling near 0.999, and its adopted figure comes from restricting attention to four features. A certificate can take the same step. The auditor declares the columns it matched on, and the checker reports a narrower result: no rule that uses only those columns reaches the target. In the loan example with a requested-amount column added, matching on the three original columns gives 63 again.

The second auditor never looks at what it drops, and on 28 supported tasks the column it dropped carried the signal. Its claims are true as worded and wrong as conclusions. The checker states the scope of a claim and keeps narrower results out of the certified count. It cannot judge the choice of columns. That judgment stays with a reviewer, as it does in the post.

7Limitations

  • A script is the best auditor here. The first row of Table 2 is a group-by a few lines long. On clean tables a language model adds nothing to it. The contribution is the certificate format and its checker.
  • Narrower certificates need a reviewer. Only a claim about every solver is safe to accept unread. Table 3 shows a careless choice of columns passing the checker.
  • The bound refutes a target and does not replace it. Figure 2 shows the gap between what is provable and what is realistic.
  • Target size leaks a little. The best rule that looks only at surface features, such as how large the target is, reaches 70% accuracy where always guessing the majority reaches 60%.
  • Accuracy only. The count is exact for accuracy. The post applies its grouping to a pairwise F1 score, and another of its cases uses average precision. Certificates for those metrics are not worked out here.
  • Small and synthetic. Twenty scenarios, five rules, one author.

8An earlier version that failed

The first version used short text tasks. An auditor had to give two readings of the documents that led to different answers. Before any model was run, a regular expression was tried against it. It labelled all 80 tasks correctly and produced a valid pair of readings for each. A benchmark that string matching solves cannot compare auditors.

That version stays in the repository with the result pinned as a test, and the second version measures shortcut baselines before anything else.

9An experiment that has not been run

The repository includes prompts and a scorer for one comparison: ask a model for a verdict alone, or ask it for a verdict plus a certificate. In the second condition only certified claims count, so false alarms are zero by construction.

The open questions are how often the verdict-only condition raises a false alarm on the hard negatives, and how much recall the certificate requirement costs. If the verdict-only condition raises none, certificates buy nothing on this benchmark. That run is not scheduled.

10Reproducing the results

Python 3.9 or later, standard library only. Code and data are in the repository.[2]

python3 -m unittest discover -s tests
python3 ceiling.py demo
python3 ceiling.py control --split all
